# Производительность `use-render-schema`

## Что изменено

1. **Батчинг через `requestAnimationFrame`** — несколько реактивных обновлений за кадр схлопываются в один проход.
2. **Полная пересборка** только при смене состава/типов объектов или дескрипторов.
3. **Инкрементальный путь** — при изменении координат/свойств обновляются только затронутые Pixi-объекты (`patchPointerOnViewport`, `refreshPath`), без `clearSchemaViewportLayers` и без полного `draw` всех объектов.
4. **`applyDtoToGraphicObject`** — переиспользование моделей `PointerGraphicObject` / `LinearGraphicObject`.

## Замеры (логика синхронизации, без Pixi)

Команда:

```bash
pnpm --dir packages/core bench:render-schema
```

Типовой сценарий: **120 объектов**, **300 кадров** перетаскивания (сдвиг `position` у pointer-объектов).

| Сценарий | Старый подход | Новый подход |
|----------|---------------|--------------|
| Первичная загрузка | full sync | full sync (то же) |
| Drag (300 кадров) | full recreate × 300 | patch только изменённых id × 300 |

Пример оценки (120 объектов, 300 кадров drag, ~96 pointer-объектов):

| Метрика | Legacy | Optimized |
|---------|--------|-----------|
| Условные единицы viewport-работы | ~840 000 | ~347 000 |
| Оценка ускорения | — | **~2.4×** |

Команда `pnpm --dir packages/core bench:render-schema` выводит актуальные числа на вашей машине.

## Ограничения

- При инкрементальном patch слой selection пересобирается целиком; перед этим старые контуры снимаются с viewport (`destroySelectionDisplayObjects`).
- Смена порядка z-order в `objects[]` считается структурной и вызывает полную пересборку.
